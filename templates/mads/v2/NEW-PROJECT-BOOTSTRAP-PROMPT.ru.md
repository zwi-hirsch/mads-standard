## Первоначальные действия

1. Проверь настоящее подключение к каноническому репозиторию, его ветки, исходный код, историю, API/CI, разрешения на чтение/запись, текущие правила и уже существующие процессы. Зафиксируй точный HEAD/TREE, lock-файлы и ограничения. Не заявляй, что доступ есть, пока не проверил его.
2. **Проверь наличие полного стандарта MADS v2.0 внутри этого проекта или во вложении.** Если он отсутствует, не подменяй его памятью, пересказом или выдуманным файлом и не пытайся читать приватный репозиторий example project. Сообщи `BLOCKED_MADS_BOOTSTRAP`, предложи одноразовую загрузку bootstrap-kit в этот проект, продолжай только безопасную инвентаризацию.
3. Прочитай MADS v2.0 целиком, включая нормативные разделы 18–26, шаблоны v2.0 и имеющиеся проектные документы. Проведи gap-анализ. **Не перезаписывай существующую архитектуру, код, CI, память, ветки или задачи без анализа и отдельного изменяющего PR.**
4. Подготовь проектный MADS manifest, `AGENTS.md`, собственные `memory/owner/MEMORY.md` и `memory/INDEX.md`, реестр ролей, владельцев исходных файлов и API-контрактов, Kanban MD+HTML, правила доказательств, Git-почты и статусов, конвейеры CI/Watchdog, документацию восстановления и AI Operations. Все они должны ссылаться **только на собственный проект и его Git**, не на example project.
5. Установи **один канонический Git с правом записи**. При схеме Gitea→GitHub выбери явную направленность моста, source-of-truth для main/PR/почты и правила проверки SHA/задержки зеркала. Два независимых писателя в main запрещены.
6. **Принцип ролей обязателен:** Owner и квалифицированные специалисты реализуют настоящий код и исполняемые тесты в своей области; внешний агент независимо тестирует уже написанный код, находит ошибки, исправляет и оптимизирует его. Агент не получает по умолчанию разработку новых функций или право самостоятельно менять архитектуру. Обязанности могут изменяться лишь отдельным решением владельца.
7. Для каждого специалиста-разработчика пройди полный **12-шаговый MADS admission**, а не только READ_ONLY: отдельные Git mailbox-in/out/status, role memory и source-branch → `WATCHDOG_ATTACH_READ_ONLY` и первый ACK → отдельный точный `SESSION_START` с `source_write_authorized: true`, `session_id`, монотонным `lease_epoch`, HEAD/TREE/lock/allowed_paths → второй ACK и проверка статуса → **настоящие исходные коммиты, тесты и PR**. Если разрешение заблокировано, укажи `BLOCKED_ADMISSION` и исправляй допуск; не оставляй разработчика в вечном PATCH_ONLY.
8. Назначь специалистам непересекающиеся области кода и конкретные конечные очереди (по умолчанию 5 PRIMARY + 7 RESERVE). После каждой задачи: targeted gates → source+evidence commit → push → независимая проверка remote HEAD/TREE → **проверенный delta/full Git bundle и независимое восстановление до долгой регрессии**. Пересчитывай READY и продолжай независимые безопасные задачи без микросогласований.
9. После написания кода специалистом проведи собственную source-bound приёмку, затем выдай внешнему агенту `INTEGRATION_HANDOFF` с точным SHA/TREE/lock на независимую QA, fault injection, исправления дефектов и оптимизацию. Агент работает в отдельной ветке и не меняет исходную ветку специалиста. Финальное объединение — только после приёмки Owner.
10. Подключи один детерминированный read-only Git Watchdog для зарегистрированных активных ролей; отдельные фоновые ChatGPT-задачи для каждого специалиста не создавай. Опционально один Owner-level watchdog, если возможность реально доступна. Сообщение в Git **не пробуждает** неактивный чат. Не обещай фоновые действия без реально запущенного механизма.
11. Проведи MADS-проверки **G0–G13**: Git/право записи, role ACK, source SESSION_START, изоляция ролей, резервное восстановление, READY, настоящий код, независимая QA, Owner merge, Watchdog/уведомления, восстановление новой сессии, зеркала, отделение production и синхронизация документации. Указывай `PASS / FAIL / NOT_RUN / BLOCKED` с доказательствами. Документы сами по себе — только `MADS_SOURCE_READY`, а не установленная операционная система разработки.
12. **Без отдельного разрешения** не используй production-ключи, внешние серверы, платные API, реальные пользовательские данные или новые инфраструктурные ресурсы, не выполняй deployment и не меняй защищённый main.

## Формат работы и результатов

Выполняй крупные, dependency-safe блоки задач, не ограничивайся одними предложениями. По завершении каждого прогона сообщай простыми словами, что **реально работает**, что только написано, что проверено и что осталось заблокированным. Показывай текущие Git HEAD/TREE, реальные команды/RC и источники доказательств, контрольную сумму и место доступного recovery bundle, ссылку на PR, **Kanban DONE/READY/BLOCKED/REMAINING/TOTAL** и **пять конкретных задач следующего прогона**.

**Твоя первая задача сейчас:** провести безопасную инвентаризацию и bootstrap MADS в этом репозитории. Подготовить проектные документы, рабочий backlog, разрешения и проверяемые тесты допуска; открыть draft PR вместо прямых изменений main. Не выдавать SOURCE_READY за OPERATIONAL_PILOT. Если прикреплённый стандарт или доступ на запись отсутствуют, честно отметить точный блокер, не обращаться за расширением токена к другим частным репозиториям и продолжить безопасную часть работы.
